button response

The animations live in the firmware: you pick one, and then its colours, brightness and direction. The fourteen entries and the controls each one shows are the vendor tool's own — measured by driving it and diffing the image it writes, so what you set here is what it would have stored. 0x1C holds the effect (high nibble) and the cycle speed (low nibble); 0x33 bit 7 selects the vendor's second group of names, which is why some names repeat the same id.

Colours

Seven colours, 4 bits per channel (0–15 each), so the picker can only land on 16 levels — the numbers next to it are exactly what goes into the mouse. The cycling effects walk through the ones ticked as cycle. Colour 1–6 is stored paired with the six DPI stages in the same byte (one channel each), and colour 7 shares a byte with the brightness.

Colour per DPI stage

What some effects step through as you change stage, one colour per DPI step.

One Apply writes the whole configuration — buttons, DPI, macros, profile and these lights — not just the colours: the mouse cannot be read back, so sending only some fields would leave its pointer table stale. Until you Apply, the changes stay in this browser.

Macros

No macro selected. A macro is a short sequence of key presses the mouse runs on its own when you assign it to a button — create one with New macro.

times

Run until release is the mode the held-key recipe uses: a one-step macro with the key down holds while the button is pressed (measured on the mouse). Multi-step flows, Run until click and Repeat on N are written exactly as the vendor tool writes them, but their timing has not been watched on the mouse. The mode lives inside the macro, not in the button's action byte (docs/PROTOCOL.md §5-ter). 


          

        

      

      

        

          
          
        

        

          To use a macro, pick it in the Function column of the Configuration tab — macro slots
          are only mapped in profile 1, like media and keyboard keys. Macros live in this browser and

          held key takes 42 B and a macro takes its own length, so they add up.

Saved in this browser

      

        

          
          
          
        

        

          Every change is stored in this browser (localStorage) as you make
          it, so reloading the page does not lose it; a file is only needed to carry the setup
          elsewhere. Revert throws the unsent changes away and goes back to what is stored;
          Forget deletes what is stored.

Byte probe

          Sets one byte in the image this browser is holding — nothing is sent until Apply.
          For the fields the Lighting tab does not expose: sweep 0x1C
          (effect in the high nibble, cycle time in the low one), 0x3F
          (brightness) or 0x3A (the symmetry/direction bits) and watch the
          mouse. Probes are not part of the saved configuration and are dropped on reload.
        

      

    


    

      
Keyboard keys

      

        

          
          
          
          
          
        

        

          
          
          
          
        

        

          Hold (the default) writes the vendor's own shape: twenty
          81 <key> words with action
          0x2E, no release inside, so the key goes down when you press
          the button and comes up when you let go — confirmed on the mouse. It needs the macro
          library out of the way first: the factory image keeps it in 0x400,
          the same block the button flows use, so every Apply moves it up to
          0x4C0 (liftLibrary()); otherwise the
          firmware runs the library's flow and the key is a 1 ms tap. Tap once carries its
          own release (83 <key> <delay> <key> 00 00) and
          tap while held uses 81/01 pairs. Nothing is written
          until Apply.
